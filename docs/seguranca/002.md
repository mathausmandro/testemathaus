## Achados

### G1 - Baixa - O gitleaks ainda ignora package-lock.json (allowlist padrão herdada)
- Onde: .gitleaks.toml (`[extend] useDefault = true`). O comentário diz que o "package-lock.json é varrido de propósito (S3 e S4)".
- Cenário: a configuração padrão do gitleaks, herdada por `useDefault`, tem uma allowlist global de caminhos que inclui lockfiles. O teste canário confirmou: o mesmo conteúdo com token (`resolved` com `https://u:TOKEN@...`) é detectado em `lock-copy.json` e ignorado em `package-lock.json`. Na árvore atual, o secretlint do verify cobre o lockfile, inclusive no CI. Já no **histórico**, que só o gitleaks varre, um token que tenha entrado e saído do lockfile em um commit antigo passaria sem alerta. O comentário também passa uma falsa garantia.
- Correção sugerida: escolher uma das opções. (a) Rodar o secretlint também no histórico do lockfile: `git log -p -- package-lock.json tools/lhci/package-lock.json` com saída para o secretlint via stdin. (b) Criar no .gitleaks.toml uma regra própria para credencial em URL de registro, sem herdar a allowlist de caminhos. Ou (c) pelo menos corrigir o comentário e registrar a limitação em docs/qualidade.md.

### G2 - Baixa (prevenção, vale a partir das tarefas de login) - Os artefatos do Playwright podem passar a conter sessão
- Onde: ci.yml (upload de playwright-report/ e test-results/); playwright.config.ts (`trace: "on-first-retry"`).
- Cenário: quando houver e2e autenticado (tarefas 005 a 014), o trace, o relatório HTML e as capturas de tela guardam cookies e cabeçalhos de autenticação, além do conteúdo das telas. Se o repositório for público, ou se alguém com acesso de leitura não puder ver dados, os artefatos expõem tokens de sessão. Hoje esses tokens seriam do Supabase local, de teste e descartáveis. O risco cresce se algum dia o e2e rodar contra um ambiente real ou um storageState com usuário verdadeiro.
- Correção sugerida: manter o e2e sempre contra o Supabase local, com usuários fictícios. Nunca publicar `storageState`/`.auth/` como artefato e adicionar esse caminho ao .gitignore. Manter o repositório privado. Revisar esta regra na tarefa do e2e autenticado.

### G3 - Baixa - Falta a verificação de SUPABASE_SECRET_KEY em código de cliente
- Onde: tests/security/ (só env-example.test.ts).
- Cenário: a regra 2 do CLAUDE.md ainda não tem guarda automática no código. Quando src/lib/data e o login existirem, um `process.env.SUPABASE_SECRET_KEY` em arquivo com `"use client"`, ou um import de módulo de servidor em componente de cliente, não seria pego pelo pipeline.
- Correção sugerida: até a tarefa 011, criar tests/security/secret-key-client.test.ts que falhe se SUPABASE_SECRET_KEY aparecer em arquivo de src/ com `"use client"`, ou em qualquer arquivo fora de módulos `server-only`. Também é recomendável usar `import "server-only"` no cliente admin do Supabase.

### Observações (sem gravidade, para o desenvolvedor e o QA)
- O relatório do Lighthouse provavelmente não será publicado. Desde a v4.4, o upload-artifact ignora arquivos ocultos por padrão (`include-hidden-files: false`), e .lighthouseci/ é uma pasta oculta. Isso não traz risco de segurança: o efeito é deixar de cumprir o critério "relatórios como artefato". Para corrigir, use `include-hidden-files: true` só nesse upload ou mude o `outputDir` para lighthouse-report/.
- Em tests/perf/run-lighthouse.mjs, o `npm ci --prefix <LHCI_DIR>` roda com `shell: true` no Windows. Um caminho do projeto com espaço ou com metacaractere do cmd quebra o comando. Não é explorável (o caminho é da própria máquina do desenvolvedor), mas convém passar o caminho entre aspas ou usar `cwd: LHCI_DIR` no lugar de `--prefix`.
- O Lighthouse roda o Chrome com `--no-sandbox`. É aceitável porque só navega em localhost, com conteúdo nosso.
- Sugestão: incluir `npm audit --prefix tools/lhci --audit-level=critical` como sinal informativo, para que uma vulnerabilidade **crítica** nova no LHCI apareça sem bloquear o pipeline pelos 13 altos já aceitos.
